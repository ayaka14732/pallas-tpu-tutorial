# Pallas TPU Kernel 开发教程

> **本教程已停止更新，只作存档。** 本教程面向 TPU v4。工作组已将它改写为面向 TPU v7x 的版本，并转为内部开发；这里的内容保留归档时的状态，不再修订，其中的结论和数字也不会随新的实验更新。

## 前言

本教程面向熟悉 JAX、了解 GPU kernel 开发，希望进一步掌握 TPU kernel 开发的读者。你将从最基础的概念出发，逐步掌握在 TPU 上使用 Pallas 编写高性能 kernel 的能力。

### 为什么要学习 Pallas TPU Kernel 开发

XLA 是一个成功的编译器。它把 JAX 程序降低为 HLO 计算图，自动完成算子融合、布局分配、内存规划、指令调度，以及跨芯片的分片与通信。研究者只需写出数学意义上的计算，就能在 TPU 上获得可观的性能。

在过去很长的一段时间里，Google 内外大量模型的训练与推理都直接建立在 XLA 编译器之上。某个模式的性能不理想时，可以在 XLA 中增加一条融合规则，或编写一个新的优化 pass，而一旦合入，所有基于 XLA 的模型都能一同受益。相比之下，为单个模型维护一个 custom kernel 显得成本高、收益小。于是，模型开发者只负责编写 JAX 程序，编译器团队负责性能；TPU 的内存分块、片上布局与流水线调度全部封装在编译器内部，是一个“黑盒”。这个黑盒本身是一种合理的抽象，它以极低的开发成本换来了“足够好”的性能，而在当时，“足够好”确实已经足够。

大模型时代改变了这一权衡。如今没有“能运行就够了”，只有充分优化。一次多余的 HBM 往返、一个无法融合的中间张量、一段没有重叠起来的通信与计算，乘上数万颗芯片和数月训练时间，都会变成真实而巨大的成本。然而，XLA 是通用编译器，必须服务广泛的模型，依靠通用分析和优化 pass 寻找解法，在保证所有模型正确的前提下做出保守的决策。它采用的算法未必最好；即便算法合适，其切块、布局与流水线参数也不会是为当前任务专门挑选的。曾经让开发者免于操心硬件细节的黑盒，此时变成了阻挡开发者触及硬件能力的墙。

以 top-k 为例：在特定的形状下，XLA 把整行连同下标一起排序后再取前 k 个。实际上，改用没有依赖链的秩计数，周期数只需 XLA 的五分之一。在性能优化中，我们可以参照 XLA 写出与之相当的程序，但进一步只有从更底层的视角才能判断。原生 XLA 是必须越过的底线，一个比 XLA 还慢的 kernel 没有存在的理由。

Pallas 正是为此而生。它打破了原生 XLA 的黑盒限制，把硬件控制权交还给开发者：与其等待某个模式被编译器识别、等待一个新的优化 pass 被设计和部署，不如由最了解模型与工作负载的人直接写出所需的 kernel。Pallas 给研究者的正是这一级控制权：决定数据以什么布局进入 TC VMEM，HBM 与 TC VMEM 之间的 DMA 如何同 MXU 计算重叠，何时同步，以及多个阶段如何组成软件流水线；同时，这些 kernel 仍然能够接受 JAX 程序变换，并进入统一的训练、推理与分布式执行系统。

掌握 Pallas，也是在参与 TPU 的软硬件协同设计。哪些数据流反复受制于带宽，哪些布局转换消耗过高，哪些同步原语缺失，怎样的片上存储、矩阵单元和互联才能支撑下一代工作负载，这些问题只有通过真实 kernel 才会暴露。今天对 Pallas kernel 的深入研究，不只是优化现有 TPU，也会为 TPU v11 乃至更远期 TPU 的指令、存储层级、互联与编程模型提供设计依据。

需要注意的是，由于 Pallas 表面上沿用了 JAX 的语法形式，许多开发者容易形成路径依赖，试图用高层自动微分和向量化思维来套用它，产生水土不服。理解 Pallas 的前提，是放下 JAX 的纯函数数学直觉，建立对 TPU 具体物理部件的意识。

### 学习的目的是服务 TPU 硬件本身

我们学习的根本目的只有一个：最大化 TPU 的实际性能。我们选择 Pallas，是因为当前 Pallas 是最贴近直接控制硬件的入口，而不是因为我们认同或依赖 Pallas 这个项目本身的能力范围。

必须说明一个现实：Google 的 JAX 团队首先服务的是内部的工作负载，对外部使用者的诉求并不总是积极响应，在资源投入上也较为保守。在本教程编写的过程中，我们报告的许多问题常常石沉大海，至今未获任何回复。这意味着，如果我们的优化需求依赖官方的主动投入，我们大概率会长期等待，或者根本等不到。

更为严重的是，Pallas 开发的重心大多着眼于更高层的便利：BlockSpec 与 grid 简化了分块，`pltpu.emit_pipeline` 封装了软件流水线，近一年多来持续投入的 fuser 则将 kernel 前后的 JAX 运算融合进 kernel。这些接口减少了样板代码，但进一步限制了硬件能力的发挥。在 AI agent 时代，即使是编写 tpuasm 这样的复杂任务，agent 都能够游刃有余，更遑论分块、软件流水线这些 API 提供的“语法糖”；而 agent 无法代劳的，是 API 本身无法表达的硬件能力。构建抽象高层 API 这样的工作，早已不能代表 TPU 性能工程的前进方向。

在性能优化的实际工作中，人们越来越意识到：如果说原生 XLA 暴露给用户的是高层接口，那么 Pallas 仍然不够底层，只能算作中层。它让开发者决定如何分块、数据放在哪一级存储、何时发起 DMA、何时同步；但每个运算选用哪条指令、哪些指令放入同一个 bundle、寄存器如何分配、分支延迟槽中放置什么、程序在指令存储中如何布局，仍然取决于 Mosaic 编译器、以及更底层的 XLA 编译器的基础设施。

“成也 XLA，败也 XLA”，正因为 XLA 编译器足够成功，“优化已由编译器完成”逐渐成为一种默认的假设。一旦默认底层已被 XLA 编译器妥善处理，便很少有人再去审视编译器的实际行为是否合理；久而久之，软件栈中积累了大量未经审视的盲区。可以说，过了 Pallas，优化才刚刚开始。以一个 MoE 专家的计算块为例，在保留全部计算指令、累加次序与舍入点的前提下，仅重新安排指令的先后、组包与寄存器分配，指令执行周期数便减少 11.2%。所谓 TPU 性能优化，就是与 XLA 编译器斗智斗勇的艺术：找出其算法与启发式在何处不适合当前任务，再借助屏障或内联汇编加以绕开，同时保留它处理得当的部分。

因此，我们不满足于停留在 Pallas 的抽象之上，而是持续追问编译器最终生成了哪些指令、硬件还有哪些能力没有被现有软件栈暴露出来。只要 TPU 硬件具备某种能力，并且利用这种能力对我们的优化有益，我们就应当有方法把它实现出来，无论这种功能是否被 JAX 或 Pallas 的 API 支持。

学习本教程中的 Pallas 用法时，请始终记住：你在学习的不是“Pallas 允许你做什么”，而是“TPU 允许你做什么”。

## 开发环境

本教程使用 TPU v4、JAX `0.12.0.dev20261002+7fc69a22c2`、jaxlib `0.12.0.dev20261002`、libtpu `0.0.49` 和 tpuasm `0.2.1`。

虽然 TPU 已经有了更新的世代，但 TPU v4 足以承载本教程要介绍的核心思想。后续世代的具体指令、存储容量、带宽与计算吞吐会变化，但从硬件约束出发、检查编译结果、分析瓶颈并验证优化的方法仍然适用。在 TPU v4 上建立起这套方法，迁移到新的 TPU 时，就能根据新的硬件特性重新推导实现与调优策略。
