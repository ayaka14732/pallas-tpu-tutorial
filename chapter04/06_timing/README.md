# 随机数的计时

前几节用指令数比较了不同的生成方法。本节用第三章的方法实测：`vrng` 自身的时序，以及在 kernel 中连续生成时，各种方法每个 TC VREG 要多少周期。

## vrng 的时序

本小节实验[源码](01_tpuasm_vrng_timing.py)、[输出](01_tpuasm_vrng_timing.txt)。

与第三章第 6 节相同，用 `LccProbe` 插入手写片段，`setup` 中先 `setrngseed`。读数 `(R1 − R0, R2 − R0)`：

| 片段 | 读数 | 结论 |
| --- | --- | --- |
| `vrng` 后紧接使用其结果的 `vadd` | (3, 15) | 没有等待：结果下一个周期就可用 |
| 连续 k 条 `vrng`，k = 1、2、4、8、16 | R2 = 14、21、37、69、133 | 每多一条加 8 个周期 |
| `va0` 与 `va1` 交替，k = 2、8 | R2 = 21、69 | 与全在 `va0` 相同 |
| k 组“`vrng` + 一条无关的 `vadd`”，k = 2、4 | R2 = 22、38 | `vadd` 不增加时间 |
| `vrng` 后紧接 `getrngseed` 或 `setrngseed` | (3, 21) | 同样等 8 个周期 |
| `setrngseed` 后紧接 `vrng` | (3, 23) | `vrng` 晚 10 个周期 |

`vrng` 的发射间隔是 8 个周期：一条 `vrng` 让每个生成器连续走 8 步（第 1 节），每个周期一步。两个槽共用同一个生成器，换到 `va1` 不能并行。间隔中的空闲周期可以发射其他向量运算。按第三章第 6 节的模型，它与 XLU 的转置相似：一个单元每 8 个周期接收一次，期间不挡住其他指令。

由此，硬件生成器的吞吐上限是每 8 个周期 4 KiB，即每周期 512 字节，按 1.05 GHz 约 540 GB/s。

## 在 kernel 中连续生成

本小节实验[源码](02_pallas_generation_rate.py)、[输出](02_pallas_generation_rate.txt)。

kernel 在 `pl.loop` 中反复生成，每次 `rows` 行，结果异或进同一个 buffer，使编译器不能删去任何一次生成：

```python
pltpu.prng_seed(1)
acc_vmem[...] = jnp.zeros((rows, 128), jnp.uint32)

@pl.loop(0, steps)
def _(step: jax.Array) -> None:
    acc_vmem[...] = acc_vmem[...] ^ generate(rows, step)
```

每种方法编译两个 kernel，分别生成 64 个和 576 个 TC VREG，取 XProf 中 kernel 时间（第三章第 1 节）之差，除以多生成的 512 个，消去种子混合、DMA 等固定开销。实验只改 `generate` 和 `rows`，十种方法见源码中的 `METHODS`。

同时统计清单：`pl.loop` 不展开，循环体在清单中只出现一次；与循环体只生成全零的 kernel 相比，多出的计算指令除以每次的 TC VREG 数，就是每个 TC VREG 的计算指令。两个向量 ALU 槽每周期各发射一条，指令数的一半是只受 ALU 限制时的周期下限。

| 方法 | 实测：每个 TC VREG 的周期 | 吞吐 | 计算指令 | ALU 下限（指令数 / 2） |
| --- | ---: | ---: | ---: | ---: |
| 硬件 `vrng` | 8.4 | 514 GB/s | 2.0 | 1.0 |
| `vrng` → 均匀分布 | 8.6 | 499 GB/s | 6.0 | 3.0 |
| `vrng` → 伯努利（整数阈值） | 8.5 | 506 GB/s | 5.1 | 2.6 |
| `vrng` → 指数分布 | 10.0 | 430 GB/s | 10.0 | 5.0 |
| `vrng` → Gumbel 分布 | 11.5 | 374 GB/s | 14.0 | 7.0 |
| `vrng` → 正态分布（`stateful_normal`） | 36.9 | 117 GB/s | 71.1 | 35.6 |
| `vrng` → 正态分布（Box–Muller） | 62.8 | 69 GB/s | 120.9 | 60.4 |
| Philox 4x32，每次 64 行 | 137.7 | 31 GB/s | 268.6 | 134.3 |
| threefry2x32，每次 64 行 | 119.7 | 36 GB/s | 139.2 | 69.6 |
| threefry2x32，每次 16 行 | 293.0 | 15 GB/s | 193.5 | 96.8 |

这里的计算指令包括异或进 buffer 等循环本身的指令，比第 4、5 节单独统计的变换略多。按瓶颈可以分成三类：

**生成器受限。** `vrng`、均匀分布、伯努利都在 8.4–8.6 个周期，ALU 下限只有 1–3 个周期：瓶颈是 `vrng` 每 8 个周期一条的发射间隔，变换的指令完全藏在间隔里。指数分布与 Gumbel 分布的 10.0、11.5 个周期略超过 8，也远高于 ALU 下限，多出的部分本实验没有进一步分解；`vlog2` 的发射间隔是 2 个周期（第三章第 6 节），每个 TC VREG 一到两条，也不是瓶颈。

**ALU 受限。** 两种正态分布与 Philox 的实测与 ALU 下限只差 1–4 个周期：两个向量 ALU 槽几乎每个周期都在发射，生成器反而闲着。要让这类变换更快，只能减少指令，例如选择不需要正弦、余弦的方法（第 5 节）。

**依赖与槽位受限。** threefry2x32 的实测比 ALU 下限多 70% 以上。原因之一是槽位：tpuasm 的指令索引中，`vshll`、`vshrl` 只出现在 `va1`，不能在 `va0` 发射。统计每次 64 行的 kernel 段（含少量循环外的指令）：`va1` 上有 `vshll` 208 条、`vshrl` 201 条，`va0` 上有 `vadd` 310 条、`vor` 179 条、`vxor` 144 条。两个槽的指令数并不均衡，每个 TC VREG 的 `va0` 就有约 80 条，下限实际上是 80 而不是 70。其余的差距来自 hash 每一轮的依赖链（第 4 节）和溢出到 TC VMEM 的读写。每次只生成 16 行时更慢：每次只有 2 个 TC VREG 可以交错执行，依赖链无法被掩盖，而 `fold_in` 的固定开销只分摊到 2 个 TC VREG 上。

## 结论

对比第二章第 2 节：HBM 读入一个 TC VREG 约需 4 个周期。所以：

- 用 `vrng` 在 kernel 内生成均匀分布或伯努利掩码，每个 TC VREG 约 8.5 个周期，比从 HBM 读入预先生成的随机数慢一倍；但它不占 HBM 带宽，可以与其他读写、计算并行，而生成器在 8 个周期的间隔中只占用极少的 ALU。
- 正态分布这类变换受 ALU 限制，会与 kernel 的其他向量计算争用两个 ALU 槽；在计算密集的 kernel 中，它的真实代价就是这些指令本身。
- threefry2x32 每个 TC VREG 约 120 个周期，比 HBM 读入慢约 30 倍，只在需要与 `jax.random` 逐位一致、或需要按位置寻址时才值得；使用时每次至少生成几十行，让多个 TC VREG 交错掩盖依赖链。

这些计时补充了[研究报告 57](../../../pallas-tpu-readings-dev/research_reports/57_tpu_v4_rng.md) 未测的时序部分。
